## Item 3 note: end-to-end latency

The service answers well inside the budget under 3× load, but callers measured from outside saw
multi-second tails. Before a clinic depends on it:
- run the load test from inside the platform's region (a one-off service on the private network)
  to separate the edge and network from the service's own queueing;
- run voice-gateway with **2 replicas** in production, as the architecture plans, each with a
  pool of 8 (`app_voice` allows 20 connections), so a burst of simultaneous calls doesn't wait
  for a database connection;
- keep the voice provider's tool timeouts above the 1.5 s budget (the agent config's
  `timeout_ms`), so a slow answer is the service's fallback line, not a provider error.
